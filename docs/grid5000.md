# Running on Grid'5000

Grid'5000 is for approved research and education only; read the
[usage policy](https://www.grid5000.fr/w/Grid5000%3AUsagePolicy) first.

## One-time setup on a site frontend

```bash
ssh nancy
git clone https://github.com/NoeFlandre/benchmark-llms-landuse-relevance.git
cd benchmark-llms-landuse-relevance
curl -LsSf https://astral.sh/uv/install.sh | sh
```

The frontend is for checkout, submission, and monitoring only. Everything heavy runs
on a reserved node.

## Submit

```bash
usagepolicycheck -t
scripts/g5k_submit.sh 1:00     # one GPU, one hour
oarstat -u
```

For a weighted multi-site run, review every remote command first and then submit the
same fixed shard plan:

```bash
scripts/g5k_submit_multisite.sh --sites-config scripts/g5k_sites.json --dry-run
scripts/g5k_submit_multisite.sh --sites-config scripts/g5k_sites.json --walltime 1:00
```

Submission wrappers request Grid'5000's `night` job type by default, which keeps the
large sweep in the policy-compatible night/weekend window. They request a GPU with
compute capability 7 or newer and at least 23,040 MiB of memory. This excludes the
older GTX 1080 Ti/P100 class and leaves room for the largest rostered models; override
`LRB_JOB_TYPE` or `LRB_GPU_FILTER` only after checking the policy, site inventory, and
runtime compatibility.

The site list is explicit and each configured weight becomes that site's share of the
deterministic shard slots. The script runs `usagepolicycheck -t` on every site before
submission; dry-run mode performs no SSH or OAR mutation.

`scripts/g5k_node_run.sh` runs on the node: it syncs the pinned environment, validates
the 85-language inventory, and benchmarks each rostered model-language pair with the
active 4096-token budget. Submission wrappers place live checkpoints in the separate
`results-live/` tree so the repository's archive-only results are never mixed into a
collection. Results are checkpointed as
`results-live/<language>/<namespace>__<model>.json`; re-running the job skips valid pairs
already present, so a walltime overrun is resumed rather than repeated.

To finish one model before moving to the next, set `LRB_MODEL_ID` when submitting a
wave. The same shard plan then applies only to that model's languages; valid existing
checkpoints are still skipped. This works for both generative models and scoring
models; the node wrapper dispatches scoring IDs to `lrb score` and records throughput
and peak CUDA VRAM:

```bash
LRB_MODEL_ID=Alibaba-NLP/gte-multilingual-reranker-base \
  scripts/g5k_submit_multisite.sh --sites-config scripts/g5k_sites.json --walltime 4:00
```

Measure the reservation before starting a GPU run:

```bash
scripts/g5k_node_run.sh --dry-run
```

The dry run prints language count, total rows, model-language pair count, estimated
prompts, batch size, and token budget without loading a model. That is 85 languages
times the roster size in pairs, at 300 prompts each; a focused model run is 85 pairs and
25,500 prompts before completed checkpoints are skipped. The pair checkpoints, rather
than a single model file, are the completion evidence.

For multiple nodes, assign disjoint deterministic shards:

```bash
LRB_SHARD_INDEX=0 LRB_SHARD_COUNT=4 scripts/g5k_node_run.sh
LRB_SHARD_INDEX=1 LRB_SHARD_COUNT=4 scripts/g5k_node_run.sh
```

The node script reports both the total and assigned pair counts. Each node invokes the
same sorted planner, so shard unions are complete and non-overlapping; inspect
`uv run lrb status --results-dir results-live` before collecting a release.

The node wrapper exports `USE_TF=0` for Laya's PyTorch loader. Laya is loaded through
its official SDK from the pinned Hub snapshot; its typed `noul` calls are grouped in
small shared-state batches and report the checkpoint's 1,024-token context.

The Hugging Face cache lives on node-local `/tmp` scratch (`HF_HOME`), which is wiped
between jobs — weights are re-fetched, results are not.

## Collect and publish

`/home` is site-local, quota-limited, and not backed up, so results leave Grid'5000
as soon as the job ends:

```bash
scp -r nancy:benchmark-llms-landuse-relevance/results-live ./results-nancy
scp -r grenoble:benchmark-llms-landuse-relevance/results-live ./results-grenoble
uv run python scripts/g5k_collect.py \
  --site nancy=results-nancy \
  --site grenoble=results-grenoble \
  --output results
uv run lrb report --results-dir benchmark-runs/merged
uv run python scripts/snapshot_status.py benchmark-runs/merged \
  --model-id ... # repeat for every model in the release roster
uv run lrb publish NoeFlandre/benchmark-llms-landuse-relevance \
  --results-dir benchmark-runs/merged
```

`snapshot_status.py` rewrites `SNAPSHOT_STATUS.md` from the merged tree. `lrb publish`
does not touch that file, so skipping the step republishes the previous coverage claim.

For a scoring-only wave, pass explicit model IDs; the collector's default remains the
generative roster for backward compatibility:

```bash
uv run python scripts/g5k_collect.py \
  --model-id convaiinnovations/laya-multilingual \
  --model-id Alibaba-NLP/gte-multilingual-reranker-base \
  --model-id mixedbread-ai/mxbai-rerank-base-v2 \
  --site nancy-laya=results-nancy-laya \
  --site grenoble-laya=results-grenoble-laya \
  --site nancy-gte=results-nancy-gte \
  --site grenoble-gte=results-grenoble-gte \
  --site nancy-mxbai=results-nancy-mxbai \
  --site grenoble-mxbai=results-grenoble-mxbai \
  --output benchmark-runs/scoring
```

Then release anything still held:

```bash
oardel JOB_ID     # only if the job is still running
usagepolicycheck -t
```
